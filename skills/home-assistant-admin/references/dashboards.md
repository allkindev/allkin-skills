# Dashboards

## Before drawing

Ask, in one form: who looks at it and on what (a phone in the hand, a tablet
on a wall, a computer), what they want to see at a glance, what they want to
do from it, and whether it replaces something or comes beside it. A dashboard
"with everything" is the one Home Assistant already generates.

## Commands

| Command | Fields | |
|---|---|---|
| `lovelace/dashboards/list` | | each: `id`, `url_path`, `title`, `mode` (`storage` or `yaml`), `show_in_sidebar`, `require_admin` |
| `lovelace/config` | `url_path` (null for the default one) | its whole configuration; `config_not_found` means it was never saved: it is generated |
| `lovelace/resources` | | the custom cards installed |
| `lovelace/dashboards/create` | `url_path` (must contain a hyphen: `maison-tablette`), `title`, `icon`, `show_in_sidebar`, `require_admin`, `mode`: `"storage"` | a card |
| `lovelace/dashboards/update` / `delete` | `dashboard_id`, then the fields | a card |
| `lovelace/config/save` | `url_path`, `config` | a card — **replaces the whole dashboard** |

Rules that follow from the table:

- `save` replaces everything: always **read, change, save**, never save a
  fragment. Before saving over an existing dashboard, write its configuration
  in `home/<service-id>/dashboards/<url_path>-<date>.json`.
- The **default dashboard** (`url_path` null) is generated by Home Assistant
  until someone saves it; after that it no longer follows new devices. Do not
  save it unless the user asked for exactly that — create a new dashboard.
- A dashboard in `yaml` mode cannot be saved through the API: say where its
  file is.
- Only use a card type that exists here: the built-in ones below, or a custom
  one present in `lovelace/resources`. Never a card on an entity you have not
  read.

## Shape

One view per use, not per technology: Home, a floor or a room, Energy,
Security. In a view, the `sections` layout: each section a `grid` of cards
under a heading, which reflows by itself from a phone to a wide screen.

```json
{ "views": [ {
    "title": "Maison", "path": "maison", "icon": "mdi:home",
    "type": "sections", "max_columns": 3,
    "sections": [ {
      "type": "grid",
      "cards": [
        { "type": "heading", "heading": "Salon", "icon": "mdi:sofa" },
        { "type": "tile", "entity": "light.lustre_salon" },
        { "type": "tile", "entity": "sensor.temp_salon" },
        { "type": "tile", "entity": "cover.volet_salon", "features": [ { "type": "cover-open-close" } ] } ] } ] } ] }
```

Built-in cards worth knowing:

| Card | For |
|---|---|
| `tile` | almost every entity: state, a tap to toggle, optional features (brightness, cover buttons, target temperature) |
| `heading` | the title of a section |
| `area` | a room in one card: its picture or camera, its sensors, its controls |
| `thermostat`, `humidifier` | a climate device |
| `weather-forecast` | a weather entity |
| `history-graph`, `statistics-graph`, `sensor` | a value over time |
| `gauge` | one value against thresholds |
| `picture-entity`, `picture-glance` | a camera, with entities over it |
| `entities` | a plain list, for settings and helpers |
| `button` | one action (a script, a scene) |
| `markdown` | a note, a template |
| `conditional` | a card shown only in some state |

Design rules:

- **What matters first, at the top left**: the states people check (doors
  open, alarm, temperature) and the two or three things they do every day.
- **Eight to twelve tiles per section**; past that, another section or view.
- **No diagnostics** (signal quality, battery of every sensor) on a daily
  view: a "Maintenance" view holds them, with the batteries under 20 % shown
  by a `conditional` card or a template.
- **The names on screen are the entities' names**: fix a bad name in the
  registry (`references/naming.md`), not with a `name:` override on each card.
- **A wall tablet**: larger tiles, fewer of them, nothing that needs typing.

## After saving

Read the configuration back, and tell the user where it is: its title in the
sidebar, or `/<url_path>`. You cannot see how it renders: ask them to look,
on the device it was made for, and to tell you what is too small, missing or
in the wrong order. Expect a second pass — a dashboard is judged by eye.
